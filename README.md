# mtb_line_choice

山地车赛道 **AI 走线推荐** 的可行性研究与原型。

**目标**：上传一段赛道视频（优先徒步侦察视频），结合车手个人技术水平，输出个性化走线建议。

---

## 一句话结论

三维重建**不是**瓶颈（2026 年已被 Depth Anything 3 / VGGT-SLAM 这类前馈模型商品化）。
真正的瓶颈是：**"最优线"没有监督信号、抓地力在 RGB 里不可见、单目没有绝对尺度、车手模型难建。**

其中第一个有便宜的绕法，也是本项目的核心赌注：

> **多条车手的车载视频配准进同一个三维重建 → 快车手的实际轨迹本身就是"最优线"的标签。**
> 不需要人工标注，不需要 RL，不需要山地车物理引擎。
> 这相当于把 Racecraft Labs 做的事从**一维（时间差）**推广到**三维（空间差）**。

配套的产品定位修正：

> 徒步视频建**地图**（几何 + 语义 + 危险点），骑行视频建**线**（轨迹 + 速度 + 结果）。
> 只有徒步视频时，诚实的产品上限是「**赛前 course walk 数字化**」，不是「最优走线」。

推荐是**检索式**而非生成式——推荐的线一定是真人骑出来过的。这既降低技术门槛，也是受伤责任上的必要设计。

---

## Gate 阶梯

| Gate | 内容 | 通过条件 | 失败后果 |
|---|---|---|---|
| **0** | 单条手机徒步视频 → 度量三维网格 + 中心线 + 坡度/宽度剖面 | 坡度剖面误差 < 10%；台阶高度误差 < 15cm；网格里能分辨树根石头 | 项目不成立，止损 |
| **1** | 3+ 条骑行视频重定位进 Gate 0 模型，提取三维轨迹 + 速度剖面 ⚠️**核心风险在这里** | 主观"走了不同线"的弯道横向偏移差 ≥ 30cm 且方向一致；速度与 GPMF GPS 交叉验证一致 | 退回 Racecraft 式一维时间对比 |
| **2** | 按 IMU 能力包络分档，检索匹配档位里成绩最好的轨迹并叠加渲染 | 盲测中"合理且我敢骑"的比例显著高于随机基线 | — |

### 明确不做
- 从零训练"最优线"生成模型
- 山地车越野物理引擎 + RL（**堵点是仿真器不存在，不是算法不够**）
- 实时手机端推理（先离线批处理）

## 竞品空白

没有任何现有产品把**米级三维赛道**和**多车手三维轨迹**这两件事放在一起。
Racecraft 有多车手但只到时间轴；Rouvy Route Creator 有视频转三维路线但不做走线；
MTBCoach 有 IMU 动作检测但只有 GPS 级定位。

> ⚠️ 原 DeepSeek 调研里列的 7 个产品，**MotoTraice 和 ApexVision/SuperLap 查无此物，TrailSense 的描述完全错误**。详见调研文档。

```bash
pip install -e ".[viz,dev]"

python scripts/resolution_sweep.py # 分辨率极限实验
```

![Gate 1 demo output](docs/gate1_demo.png)

上图是 `mtbline demo` 的输出。上半部分是每条轨迹的横向偏移 `d` 随赛道弧长 `s` 的变化，
下半部分是各条之间的分离量——分叉点是自动找出来的，不是标注的。
**把线画在 `(s, d)` 平面上而不是叠在三维模型上，正是这个表示的意义**：
30cm 的差异在一条 120 米下坡的三维渲染里根本看不见，在这张图上一目了然。

`demo` 跑的是合成赛道，**只验证分析层**（中心线拟合 / `(s,d)` 投影 / Gate 判定），
不验证 DA3 能不能重建森林、hloc 能不能把糊掉的骑行视频配准进去——那正是 Gate 1 要测的东西。

## 精度目标：cm 级（2026-09-06 修订）

目标从「分辨 30cm」改为**测量精度到 cm**。`scripts/precision_budget.py` 做了完整误差预算，
结论是这个目标**可达**，而且比想象的便宜：

| 误差来源 | 传递到 `d` 的比例 | 含义 |
|---|---|---|
| 完美输入 | **0.00 cm** | 分析层本身是精确的，不是瓶颈 |
| **每条独立的配准误差** | **~0.45 : 1** | **唯一需要工程投入的地方**。2cm 配准 → 亚 cm 的 `d` |
| 全局地图误差（各条共有） | **~1 : 250** | 整体平移 1 米，`d` 只动 0.4cm |
| 中心线平滑窗口 | 无影响（16 倍范围内） | 不是精度旋钮，别调 |

**最重要的一条**：`d` 是相对于「用同一批轨迹拟合出来的中心线」测的，所以**所有条共有的误差会自己抵消**。

> cm 级的 `d` **不需要**赛道的绝对重建精度到 cm，
> 只需要**多条轨迹在同一张图里的相对配准一致到 cm**。
> 这便宜得多，而且正是 hloc 对着一张公共地图做重定位的看家本领。
> （绝对尺度仍然只能靠 telemetry，但绝对**精度**几乎无所谓。）

### 但 cm 精度买不到什么

车手自身的运行间摆动约 35cm。这不是误差，是这项运动本身——再精确的测量也不会让它变小。

> ✅ 买得到：**群体**陈述变得锋利。群均值的标准误是 `35/√N` cm，25 条时约 7cm，
>    于是「快组的线比慢组内切 15cm」这种话是站得住的。
> ❌ 买不到：**单条**归因。若某车手自己的几条run就散布 35cm，
>    「你这条内切了 12cm」描述的是这位车手的波动，不是他的选择。
>    解法不是提高精度，而是**同一车手取多条求平均后再下判断**。

## 已经跑出来的结论

`scripts/resolution_sweep.py` 在合成数据上扫了「分叉大小 × 重定位漂移 × 样本数」：

- **Gate 1a（~2m 分叉）离极限还很远**。即使重定位漂移到 0.5m 仍然 100% 正确分组。
  → **如果真实 Gate 1a 失败，原因一定在重建或重定位，不在分析层。**
- **Gate 1b（~30cm）是另一类问题，而且加数据救不了**。逐条准确率卡在 ~93% 不动，
  因为在这个尺度上**分叉比车手自身的摆动还小**（0.30m vs 0.35m）——大约每 14 条里有 1 条，
  车手是真的骑到了另一边。这不是工程误差，这是这项运动本身。

**产品后果（重要）**：30cm 尺度上只能做群体陈述，不能做个体陈述。

> ✅ 「这段最快的一批车手，内线比其他人多切约 30cm」
> ❌ 「你这里走错线了」

个体归因只在分离量大于车手摆动时才站得住——按这个模型大约是 **0.6m 以上**。
**采集目标随之改为每段 ≥10 条（每支 5 条），不是原计划的 3 条。**

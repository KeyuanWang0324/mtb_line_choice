# 山地车 AI 走线推荐：深度调研（2026-09-04）

> 本文是对 `deepseek_markdown_20260904_26ec0d.md` 的核查与扩展。
> 结论先行：**原文对"卡在哪"的判断是反的**——三维重建现在是最容易的一环，
> 真正的瓶颈是"最优线"的监督信号、车手模型、以及 RGB 看不见的抓地力。
> 另外原文列举的 7 个产品里，**2 个不存在，1 个描述完全错误**。

## 一、事实核查：原文列举的产品

|---|---|---|
| **Racecraft Labs** | ✅ 真实，且描述准确 | DH 速降专用 iOS/Android app。用 ML 对齐两段车载视频，逐帧算时间差，自动建议起点/终点/分段点，支持队内共享、公开排行榜、比赛期间"私密跑"（上榜但不公开视频）。创始人是前 Meta AI 工程师。**关键细节：它明确放弃 GPS，因为 GPS 精度不足以做速降计时** |

## 二、原文最大的判断错误

原文列的四条"为什么没人做出来"：三维场景理解难、缺标注数据、个性化难、车种差异。

**第一条已经不成立了。** 2024–2026 这两年，单目视频 → 稠密三维几何被前馈式基础模型彻底商品化了：

- **Depth Anything 3**（arXiv 2511.10647）：任意数量视图、有无相机位姿都行，直接出空间几何。在视觉几何基准上全面 SOTA，**相机位姿精度比 VGGT 高 44.3%，几何精度高 25.1%**。DA3-metric 在户外场景（公认最难的度量深度域）表现最好
- **VGGT-SLAM 2.0**（2026）、**MASt3R-SLAM**、**EC3R-SLAM**、**SLAM3R**：实时稠密单目 SLAM，直接吃 RGB 视频出稠密点云 + 轨迹
- 长视频的流式变体（Spann3R / CUT3R / Point3R / StreamVGGT / WinT3R）专门解决"一条 5 分钟赛道视频显存爆掉"的问题
- **MASt3R-Fusion**：前馈视觉模型 + IMU + GNSS 紧耦合——正好对应 GoPro 视频里自带的传感器流

也就是说，"从徒步视频重建赛道的坡度、路面起伏、障碍物位置"，今天是一条**跑现成开源模型**的路，不是研究课题。原文把它当成主要障碍，是把 2022 年的认知带到了 2026 年。

**第三条（车种差异 / 山地车比赛车复杂）是对的，而且被低估了。**

## 三、真正的四个瓶颈

### 瓶颈 1：没有"最优线"的监督信号 —— 但这个问题有便宜的绕法

原文说"需要海量由专业车手标注最优走线的视频，成本高昂"。这是把问题想成了监督学习。

**更好的思路：快车手的实际轨迹本身就是标签。**

同一段赛道上 20 条不同人的车载视频，如果都配准进同一个三维重建里，就得到 20 条三维轨迹 + 20 个成绩。跑得快的那几条轨迹，经验上就是这条赛道的好线。不需要任何人手工标注，只需要：

1. 建一次赛道的三维模型（可以用徒步视频，质量最好）
2. 把每条骑行视频**重定位（relocalize）**进这个模型 → 得到六自由度轨迹
3. 用分段计时给轨迹排序

**这本质上是把 Racecraft Labs 做的事从一维（时间差）推广到三维（空间差）。** Racecraft 已经证明了"多条车载视频自动对齐分段"在产品上跑得通、DH 圈子愿意用。缺的那一步是"对齐到空间"而不只是"对齐到时间轴"，而这一步恰好就是上面那批 SLAM/重定位模型的标准能力。

这是我认为整个项目**唯一真正有护城河、又确实可做**的点。

### 瓶颈 2：抓地力在 RGB 里是不可见的

这是原文完全没提、但实际最致命的一条。

三维重建能给你几何：坡度、弯道半径、台阶高度、树根位置。它**给不了**：这块岩板湿了滑不滑、这个弯的浮土有多厚、这条树根在雨后能不能压、路面是硬包还是松散。而山地车的走线选择里，这些东西的权重不比几何低。

- BikeScout 的思路（OSM 路面标签 + 天气预测泥泞度）是个部分解，粒度是整条路线级别，不是米级
- TrailSense 那类 IMU 传感器能事后**测量**颠簸/抓地（振动谱、打滑），但只能记录已骑过的
- 现实的做法：把"抓地力"当成**从多条历史骑行的 IMU 里反推出来的赛道属性**，而不是从视频里预测的属性

### 瓶颈 3：单目重建没有绝对尺度

徒步视频重建出来的模型，尺度是任意的——"这个台阶 0.4 米还是 0.8 米"直接决定了建议的合理性，而单目看不出来。解法都很便宜，值得在设计里写死：

- **手机 ARKit / ARCore 的 VIO 本来就是度量的**，用手机拍徒步视频是最省事的路
- GoPro 视频内嵌 **GPMF 遥测流**：陀螺 400Hz、加速度 200Hz、GPS 18Hz。免费拿到尺度、重力方向、粗位置。Python 侧有 `py-gpmf-parser`、`telemetrik`（纯 Python 零依赖）
- 画面里的已知尺寸物体：29" 轮径、车把宽度、人的身高——天然标尺
- 气压计爬升数据校准垂直尺度

### 瓶颈 4：车手模型

原文说"需构建精确的车手数字模型"。我认为这是过度设计，而且做不出来。

更务实的替代：**不建模，做检索。** 用户上传自己过去的骑行视频/IMU 数据后，系统知道他在什么坡度下敢用多快、过弯的最大侧倾、敢不敢飞。推荐时不去"生成"最优线，而是**从已配准的历史轨迹库里，挑出速度与动作分布落在这个用户能力包络内的那条**。

这跟 RL 生成最优线的路线相比：
- 不需要山地车物理引擎（见下）
- 推荐的线一定是**真人骑出来过的**，安全性和可信度天然更高
- 冷启动只需要几条别人的视频，不需要百万步仿真

RL 那条路的现状：自行车动力学 RL 是有的（Whipple 基准模型的路径跟随 + 侧向稳定，arXiv 2407.17156 / Multibody System Dynamics 2026；2026 年还有 "Bicycle Acrobatics with Reinforcement Learning"，arXiv 2608.00880）。但这些都是**刚性路面、无悬挂、无越野轮胎接触模型**。GT Sophy 能成立是因为 Gran Turismo 是一个极其精确的赛车物理引擎；山地车没有这个东西，越野轮胎-松散地面接触模型本身就是个未解问题。**RL 路线的真实卡点是仿真器不存在，不是算法不够。**

### 附：不要指望 VLM 直接看视频给几何结论

VLM 在空间推理基准上仍然只有 50–60% 准确率。ECCV 2026 的 VLM²（arXiv 2511.20644）把原因说清楚了：语义-几何错位 + 缺乏跨帧的持久三维记忆。

**但 VLM 在语义标注上是好用的**：识别"这里是树根区/岩板/沙坑/挖起的弯墙/双跳"，把语义标签贴到重建出来的几何上。分工应该是——几何交给 DA3/SLAM，语义交给 VLM，**不要让 VLM 猜坡度**。

## 四、关于输入选择：徒步视频 vs 骑行视频

原文建议"优先支持徒步视频，因为更容易提取有效信息"。**这个判断是对的，但理由和边界需要说清楚。**

徒步视频的优势是**几何**：
- 慢速、稳定、无运动模糊 → 三维重建/高斯泼溅质量高（3DGS 的通行要求就是低运动模糊，20–200 张图）
- 可以停下来、绕着障碍物拍多个视角 → 补全遮挡
- 视线可以看向想看的地方，不受骑行动线约束

徒步视频的**根本缺陷**：它里面没有任何动力学信息。没有速度、没有载荷、没有打滑、没有"这个弯我进得去出不来"。

**所以结论应该是分工，不是二选一：**

> 徒步视频建**地图**（几何 + 语义 + 危险点），骑行视频建**线**（轨迹 + 速度 + 结果）。
> 只有徒步视频时，产品的诚实上限是"赛前侦察报告"——不是"最优走线"。

这个上限其实也已经有商业价值了，而且是原文完全没想到的定位：**赛前 course walk 的数字化**。DH 车手比赛前必走赛道，这是刚需动作，本来就是拿手机拍的。

## 七、建议路线：Gate 阶梯

原文给的"组合现有工具的人工工作流"没什么意义（用户自己就能想到）。下面是可执行的技术阶梯，每一级都有明确的证伪条件。

### Gate 0 — 几何拿得住吗
一条赛道、一段 200 米、一条手机徒步视频 → 度量三维网格 + 中心线 + 逐米坡度/宽度剖面。

**通过条件**：重建坡度剖面对比气压计/RTK 真值误差 < 10%；台阶高度误差 < 15cm；肉眼能在网格里分辨出树根和石头。
**失败则**：整个项目不成立，止损。

### Gate 1 — 轨迹配准拿得住吗（**项目的核心风险在这里**）
把 3 条以上不同人的骑行视频重定位进 Gate 0 的模型，提取三维轨迹和速度剖面。

**通过条件**：在车手主观认为"走了不同线"的弯道上，提取出的横向偏移差异 ≥ 30cm 且方向与主观一致；速度剖面与 GPMF GPS 交叉验证一致。
**失败则**：退回到 Racecraft 式的一维时间对比，产品价值大幅缩水。

### Gate 2 — 个性化与推荐
按 IMU 能力包络（最大侧倾、制动强度分布、腾空容忍度）给用户分档，从轨迹库里检索匹配档位里成绩最好的那条，叠加渲染。

**通过条件**：盲测中车手认为推荐线"合理且我敢骑"的比例显著高于随机挑一条历史轨迹。

### 明确不做
- 从零训练"最优线"生成模型
- 山地车越野物理引擎 + RL
- 实时手机端推理（先离线批处理）

## 八、风险

- **数据获取**：Gate 1 需要同一段赛道的多条车载视频。冷启动只能靠自己拍 + 找本地车队合作。Trailforks 无公开 API
- **责任**：向他人推荐走线存在受伤责任问题。产品措辞必须是"别人这样骑过"而非"你应该这样骑"，这也正好是检索式方案（而非生成式）的另一个理由
- **隐私**：Racecraft 专门做了比赛期间的"私密跑"功能，说明这个圈子对赛道情报很敏感。多用户轨迹共享需要同等设计
- **车种差异**（原文这条是对的）：轮径、行程、几何角度会显著改变可行走线。轨迹库需要按车型分层，否则 29" 长行程车的线推给 27.5" 短行程车是有害的

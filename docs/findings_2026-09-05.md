# 实测记录：DA3 在 Apple Silicon 上的可行性与模型选型（2026-09-05）

> 本文记录**实际跑出来的结果**，不是调研。
> 结论有好有坏，坏的那条（位姿精度）**尚未验证，不要当成 DA3 的评测结论**。

---

## 一、DA3 能在 M5 Pro 的 MPS 上跑 ✅

这是本轮最有价值的结果：**「先租 GPU」这一步对短片段可以跳过。**

| 模型 | 24 帧 (518×392) 推理耗时 | 每帧 |
|---|---|---|
| DA3-SMALL (34M) | 0.5–0.7 s | ~0.03 s |
| DA3-BASE | 1.2 s | ~0.05 s |
| DA3METRIC-LARGE | 1.6–1.9 s | ~0.08 s |

M5 Pro / 48GB 统一内存。DA3 的推理路径本身是设备无关的（`_get_model_device` +
`torch.autocast(device_type=...)`），只有 `torch.cuda.synchronize` 被 `device.type == "cuda"`
守卫住了，所以 `.to("mps")` 直接可用。

**48GB 统一内存反而是优势**：DA3-Streaming 官方要求 <12GB 显存，这里余量很大，
长片段不需要为显存做切窗。

### macOS 安装配方（官方 README 没写，全是坑）

```bash
python3 -m venv da3venv
da3venv/bin/pip install "numpy<2" torch torchvision einops huggingface_hub imageio \
    opencv-python safetensors omegaconf plyfile pillow trimesh typer requests \
    pillow_heif "moviepy==1.0.3" addict matplotlib evo scipy
da3venv/bin/pip install --no-deps depth-anything-3      # 关键：--no-deps

export KMP_DUPLICATE_LIB_OK=TRUE PYTORCH_ENABLE_MPS_FALLBACK=1
```

四个坑：

1. **`xformers` 在 macOS 上编译失败，但它是可以不要的**。`pyproject.toml` 把它列成硬依赖，
   实际只在 `dinov2/layers/swiglu_ffn.py` 里用，且外面包着 `try/except ImportError`，
   fallback 是纯 PyTorch 的 `SwiGLUFFN`。装好后日志打印 `using MLP layer as FFN` 即确认走了 fallback。
   → **用 `--no-deps` 装，然后手动补依赖。**
2. **DA3 钉死 `numpy<2`**，而本项目分析层用 numpy 2.5。
   → **重建环境必须独立于分析环境**。这反过来印证了 `reconstruct.py` 用子进程适配器
   而不是 in-process import 的设计是对的。
3. **`pycolmap` 触发 macOS 的 OpenMP 重复初始化**（`libomp.dylib already initialized`），
   因为 torch 和 pycolmap 各自静态链接了一份 libomp。
   官方解法 `KMP_DUPLICATE_LIB_OK=TRUE` 被明确标注为 unsafe、**可能静默产生错误结果**——
   对几何管线来说这是真实风险。目前只用于 DA3 自身推理（不碰 pycolmap 代码路径），
   但**如果以后要用 DA3 的 COLMAP 导出，这条必须重新评估**。
4. 依赖列表还漏了 `addict`、`matplotlib`、`evo`、`scipy`，且 `moviepy` 必须是 `1.0.3`。

## 二、重大修正：DA3METRIC-LARGE 不输出位姿 ⚠️

`reconstruct.py` 原来默认用 `da3metric-large`，理由是「Apache-2.0 且是 metric」。**这个默认是错的。**

实测它返回 `extrinsics=None`、`intrinsics=None`、`conf=None`——它是**纯单目 metric 深度模型，
根本不做多视图位姿估计**。而本项目最需要的恰恰是相机轨迹。

### 能力 × 许可矩阵（2026-09-05 实测 + HF 官方 license 字段核对）

| 模型 | 出位姿 | metric | 许可 | 本项目可用 |
|---|---|---|---|---|
| DA3-SMALL | ✅ | ❌ | Apache-2.0 | ✅ |
| **DA3-BASE** | ✅ | ❌ | Apache-2.0 | ✅ **现默认** |
| DA3-LARGE | ✅ | ❌ | CC BY-NC 4.0 | ❌ 不可商用 |
| DA3METRIC-LARGE | ❌ | ✅ | Apache-2.0 | ❌ 无位姿 |
| DA3-GIANT | ✅ | ❌ | CC BY-NC 4.0 | ❌ 不可商用 |

**「Apache-2.0 且 metric 且出位姿」这个组合不存在。** 可商用且能出轨迹的只有
DA3-SMALL 和 DA3-BASE，两个都不是 metric。

### 直接后果

**`telemetry.py` 从「锦上添花」变成「必需组件」。** 既然拿不到可商用的 metric 模型，
尺度就只能每次都从 GoPro GPMF 或 ARKit VIO 来。这不再是可选路径，是唯一路径。

`reconstruct.py` 已相应修改：默认改为 `da3-base`，并对无位姿模型和 NC 许可模型分别报错。

## 三、合成赛道渲染器：一个关于自相似性的教训

`scripts/render_synthetic_trail.py` 渲染一条有精确真值相机位姿的赛道走廊，
用来在没有真实素材之前调试重建环节。

**第一版渲染出来后，DA3 认为相机基本没动**——22 米的前进，重建出来的轨迹总长只有 0.03 单位。

原因不是模型的问题，是**我的场景在统计意义上是自相似的**：走廊每一米看起来都和其他每一米一样，
程序纹理是齐次的，没有任何可区分的地标。这种情况下前向平移在原理上就是不可观测的，
模型报告「没动」其实是正确的。

加入 26 个位置和颜色都独特的路边巨石后，重建轨迹长度从 0.03 单位涨到 2.9–4.5 单位。

**这个教训对真实素材同样成立**：真实赛道靠的是「那棵特定的树、那块特定的石头」来锚定平移。
如果一段素材是长直、均质、无地标的（比如密林中的直线段、雪地、沙地），
**重定位会以同样的方式失败，而且失败得很安静**。这应该进 Gate 1 的排查清单。

同理，渲染器的 `sway`（横向摆动幅度）是一个**真实的测试参数而非美术选择**：
纯前向运动是 SfM 的退化情形（基线与视线方向共线，三角化病态）。

## 四、尚未验证：位姿精度 ❌

加地标之后，24 帧 / 22 米路径上的位姿误差（相似变换对齐后）：

| 模型 | 场景 | 重建轨迹跨度 | 平均误差 | 占路径 |
|---|---|---|---|---|
| DA3-SMALL | sway 0.9 | 2.92 u | 166 cm | 7.5% |
| DA3-SMALL | sway 2.2 | 2.25 u | 339 cm | 14.9% |
| DA3-BASE | sway 0.9 | 4.56 u | 417 cm | 18.7% |
| DA3-BASE | sway 2.2 | 4.02 u | 592 cm | 26.1% |

**这些数字距离可用差得很远**（Gate 1 需要的是 30 cm 量级的分辨力），
**但不应该被当作 DA3 的评测结论**，理由：

- 更大的模型（BASE）表现比更小的（SMALL）**更差**，视差更大的场景也**更差**——
  这两个方向都与预期相反，强烈提示是**我的合成场景本身有问题**，不是模型能力问题
- 场景仍然很不真实：块状的 value noise 纹理、平面着色的球体地标、
  过于陡峭的走廊（看起来像峡谷不像赛道）、没有任何真实相机会有的畸变/曝光/景深
- 单次相似变换对齐会把局部误差和全局漂移混在一起，没有区分开

**结论：位姿精度这一格仍然是空的。** 需要真实素材（或一个真正的渲染器）才能填。
在那之前，不要基于这些数字对 DA3 或对项目可行性下任何判断。
